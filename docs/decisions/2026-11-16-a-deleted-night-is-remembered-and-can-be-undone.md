# 2026-11-16 · A deleted night is remembered, and can be undone

- **Decision:** Deleting a night on the iPhone deletes it at once and, in the same save, keeps its id as a `DeletedNight`. `insertIfNew` skips a deleted id like a saved one, so a resend from the Watch isn't saved again but still gets its receipt and the Watch lets go. For 5 seconds the system bottom toolbar says "Night deleted" with Undo, which saves the night again from a copy taken before the delete, custom name included, and removes its `DeletedNight`. With VoiceOver on, the message is read out and Undo stays until the next delete or an undo. Going to the background ends it. Only the last delete can be undone.
- **Why:** A night deleted before the Watch had its receipt came back on the next resend (#104), and a full swipe lost a night for good with no way back. Deleting straight away keeps the list and the database the same whatever happens during the 5 seconds: a crash, a quit or a failed save. Undo instead of a confirmation, as on the Watch.
- **Instead of:** Hiding deleted nights behind a flag, which keeps everything the user deleted on the phone. Sending a receipt at delete time, which misses a resend already on its way. Remembering ids in `UserDefaults`, which isn't saved together with the delete. A custom glass or `ink` pill toast, since the system toolbar already is the glass control layer.
- **Also:** The ids are kept for good, a UUID per deleted night. They could go once the Watch can no longer hold the night. Adding the `DeletedNight` model to an existing database is a lightweight migration that SwiftData does on its own, and a unit test opens a database made without it.
